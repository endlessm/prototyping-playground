# Lab

A bench for one system component at a time: the system's components in a list on the left and, for the open one, its title, description and tabs. It reads the Systems module's build data (`systems/catalog`, `systems/components`) and reuses its pieces, and lists experiments from the manifest. Only making experiments writes files, through its handler on the local dev server (`server/experiments.ts`); everything else works the same locally and on the deployed site. It has a rail button (flask icon, after Systems), and no Home block, palette entries or skills.

## Addresses

Addresses use the system's permanent ID, as Systems does:

- `/lab` opens the default system's first component, or the first active system with components; it replaces itself in the history. Without any component it says "No components yet" with **View systems**.
- `/lab/<system id>` opens that system's first component the same way, or says it has none yet.
- `/lab/<system id>/<slug>` is the component's **Overview**; `/variants`, `/playground`, `/breakdown` and `/experiments` follow it, and `/experiments/<view id>` is one experiment.

The Lab offers active systems that have components (`labSystems`, the default first, then by name). An unknown or archived system, an unknown component, or an address under a component naming no tab shows "Page not found", with the component list kept and **View components** (to `/lab`) as the way back. Tab titles read "<tab> — <component> — Lab — <studio name>", and "Page not found — Lab — <studio name>" when nothing is there.

## The frame

- `pages/system.vue` is the frame: `components/LabComponentList.vue` in the section panel (`AppSectionNav`), kept on screen while the bench changes. Its header names the open system, or the **System** picker does when more than one active system has components; then **Search components** (title and address first, then description; Escape clears it; "No matching components.") and the system's components in the Systems navigation's order, the open one highlighted. Moving to another component keeps the open tab.
- `pages/component.vue` is the bench: the component's title and description, then `components/LabTabBar.vue`, a set of links ("Component tabs", the current one `aria-current`), and the open tab beside them. It gives the tabs their component through `composables/useLabComponent.ts` (`provideLabComponent` / `useLabComponent`: the system, the component, its page data from `useComponentPages`, and `reload`).
- `utils/lab.ts` holds the addresses (`labAddress`), the tabs in order (`LAB_TABS`: id, i18n label, path), the tab an address shows (`tabAt`), the systems offered, where `/lab` lands and the list's search. The tab bar, the list and the titles all read `LAB_TABS`, so a new tab is one entry there and one child page in `module.ts`.

## Tabs

- **Overview** (`pages/overview.vue`), at the Systems page's reading width: **Open in Systems**, then the component's guide (`ComponentGuide`), Source (`ComponentSource`) and Props (`ComponentProps`), as its Systems page shows them, without the examples. Files that couldn't load are listed with **Try again** (`ComponentLoadErrors`). The Systems component page links back with **Open in Lab** while this module is on and the system is active.
- **Variants** (`pages/variants.vue`): every example of the component's examples file in a grid, in the file's order, each a `components/LabVariantCard.vue`: its title as the Systems page writes it and its `SystemPreview`, so it renders alone in the system's preview document, fails alone and follows its file on disk locally. Two columns when the bench is at least 48rem wide (a container query, so hiding the component list counts), one below. An example that needs more room takes the row: `SystemPreview` emits `wide` when the example's content is wider than its frame or something in it stretches across it (a block button, a full-width table), and the card keeps the row from then on, so the grid doesn't flip as columns change. No new authoring. Under each preview, **Show code** opens that example's own code (its `<Example>` block, dedented, highlighted by the Markdown pipeline through `ComponentGuide`) and **Copy code** (named for its variant, "Copy code for Block", for screen readers) copies it with a toast, or says the browser blocked the clipboard and to copy from Show code; the snippets come in the component page data (`snippets`), with Unix line endings. The title, preview and code row of each card are rows of the grid (`grid-rows-subgrid`), so the cards of one row line up. A component without an examples file says which file to add, as its Systems page does.
- **Playground** (`pages/playground.vue`): the component file on the stage (`components/LabPlaygroundStage.vue`, in the Systems module's `SystemPreviewFrame`: its system's preview document under the component's `playground` preview ID; new props arrive by message, so it updates in place without reloading; the component sits centred on it; it grows with the component up to 70% of the window (40% on narrow screens), then scrolls inside, and stays in view while the controls scroll, beside them on wide screens and above them on narrow ones; when nothing in it takes any room, a note under it says it may need content only code can give; props that make it throw show "This component couldn’t render." with the error until the next change), beside **Props** (`components/LabPlaygroundControls.vue`, one `LabPlaygroundControl.vue` per prop), stacked on narrow screens. `utils/playground.ts` maps each prop's metadata to a control: a union of string literals is a select (optional ones without a default offer **Default**, leaving it unset), `boolean` a switch, `string` a text field, `number` a number field, anything else a "Set in code" row with its type. The Playground always opens pre-populated, so the component never starts empty: each control's start is, first, the literal attribute its component's tag has in the `Default` example (or the first example): `label="Save"`, a bare `loading`, `:size="2"`, kept only when it fits the control. `tooling/systems/example-seeds.ts` reads them on Node, from the component's own tag rather than a wrapper around it (`UInput` inside a `UFormField`), and the component page data carries them (`seeds`); computed bindings, events, directives, `class` and `style` are left out. Then the prop's literal default; then, for text that shows (`label`, `title`, `description`, `placeholder`, `text`, or any required text) still empty, a sample from its name ("Label", "Model value"), a value for the component rather than studio copy, so it isn't translated. Seeded starts reach the stage; a value equal to its start never enters the address. Each is labelled with the prop's name, its description under it as help the control is described by, required ones marked. Changed values live in the address, one query parameter each (`?color=neutral&loading=true`), replaced rather than pushed; a seeded prop emptied or set to **Default** is an empty one (`?title=`), so it stays out instead of springing back; reading it back drops unknown props and values that don't fit, and the address is rewritten without them, and **Reset** clears them, back to the seeded values (it stays enabled, keeping the keyboard where it was, and says "Values reset" to screen readers; it is left out when no prop has a control). A prop the component changes itself (a modal closed with Escape or its close button emits `update:open`) reaches the studio as the preview document's `update` message, and its control follows. Escape in the stage brings the keyboard back to the control last used, once any overlay in it has closed, so an overlay's focus trap never keeps it there. A component without props says it has none to try. A component without a component file names the file to add; props that can't be read (a component file that doesn't compile among them; the build leaves its playground out) say so with **Try again**; a required prop with no value blocks the stage, naming it (asking for a value, or saying only code can set it, with the controls disabled).
- **Breakdown** (`pages/breakdown.vue`): how the component is built, as a tree of pieces on a dotted canvas (`components/LabBreakdownStage.vue`, fed a tree and a preview ID, so an experiment view can mount the same stage). The tree is read on Node (`tooling/systems/breakdown.ts`, `readBreakdown`, carried in the component page data as `breakdown`: the tree, or why it can't be read with **Try again**): from the component file through the `.vue` files it imports inside its system (the system's aliases, `~/` at the copied app source) down to Nuxt UI pieces, whose leaves are the theme slots their own templates render (`data-slot`), and icons. Plain HTML is skipped and its components lifted; a `v-for` tag is one node, marked as repeated. A node's ID is its path: `root` is the file, `>` enters a file (`root>UButton`, `root>StudioSidebar>USidebar`), `/` goes into a tag's content in the same file, `~2` numbers a second tag of the same name under one parent, `#` names a theme slot (`root>UButton#label`). The root card shows the component live with the Playground's opening values, in the system's preview document under the component's `breakdown` preview ID: the component file instrumented (`tooling/preview/breakdown.ts`, served as `<name>.lab-breakdown.vue` so examples and playgrounds keep the plain file), where each tree tag reports its component to the runtime's `$lab` (`tooling/preview/runtime/breakdown.ts`) and takes its `ui` and `class` through an override store. The runtime marks each piece's elements with `data-lab-node` (space-separated IDs, since a wrapper and the tag it renders share an element), reports their boxes and theme slot boxes (`nodes` message) whenever they change, and outlines the pieces the studio names (`highlight` message). Cards (`components/LabBreakdownCard.vue`) show a dotted preview inset, the name, then the file and library in monospace (`ui.<slot>` for a theme slot); a source chip on each connector says where the piece comes from (System, the system's app, Nuxt UI, the icon library, Experiment); a piece's theme slots sit in a grid under it (`utils/breakdown.ts` lays the tree out). Hovering a card lifts it and outlines its piece in the preview; clicking selects it (blue outline, its name in the toolbar); Escape or a click on the empty canvas lets go. The canvas pans (drag or scroll) and zooms (the toolbar, or ⌘/Ctrl and scroll); the toolbar (`components/LabBreakdownToolbar.vue`) also cross-fades to the component alone, kept in the address as `?view=component`.
  - **Knobs**: selecting a Nuxt UI piece or one of its theme slots turns the toolbar into its inspector (`components/LabBreakdownInspector.vue`): its name, then a knob (`components/LabKnob.vue`) for each thing the classes of its theme slots set, read from the classes the preview reports for each slot (`classes` in the `nodes` message): corners, padding (horizontal and vertical apart when the classes are), space between items, text size, weight, fill, text color, ring and size, labelled from the family and the slot ("Label text size"), each family with its own colour and icon (`utils/knobs.ts`). A piece without any says "Nothing to adjust on this piece". `tooling/preview/knobs.ts` maps classes to knobs and back (`knobsOf`, `knobClass`): only a slot's unprefixed classes (a `hover:` or `md:` class stays), values on Tailwind's scale shown in pixels, colours as Nuxt UI's semantic roles, the theme's colours with opacity steps and their shades. Drag the icon sideways, type (pixels land on the nearest step) or press the arrow keys; a colour opens the theme's colours. Every change goes to the preview at once as the `overrides` host message (node ID → slot → classes), which the runtime merges into each piece's `ui` (Nuxt UI merges them with tailwind-merge), without reloading; the preview's stylesheet names every class a knob can write (`@source inline`, `knobSafelist`), so any value renders before a file uses it. Hovering a knob draws what it changes in its colour (`knob` host message, `tooling/preview/runtime/knobs.ts`): an outline on the corners, a hatch on padding and on the space between items, an outline on anything else. Unsaved changes live in memory for the page (`composables/useBreakdownChanges.ts`: `overrides`, `pending`, `set`, `valueOf`, `reset`, `all`); **Reset** ("Discard unsaved changes") drops them and Save counts them (`components/LabBreakdownSave.vue`). On a system component Save reads **Save as experiment** and stays disabled for now.

- **Experiments** (`pages/experiments.vue`): everyone's experiments with the component, newest first, each a `components/LabExperimentCard.vue`: its live preview (`LabExperimentPreview.vue`, the view in its system's preview document through `SystemPreviewFrame`, following its file on disk locally), its name (a link to its page), who made it and the day. An experiment is an ordinary view whose first comments name the component it explores, beside its permanent identity: `<!-- @lab-experiment <system id> <component slug> <YYYY-MM-DD> -->` (`tooling/manifest/experiments.ts` reads and writes it; the day is optional). The manifest lists them in a small summary (`experiments`: view ID, title, prototype, system, component, day), so the tab needs no prototype's artifact list; a marker naming another system than its prototype's is ignored, and the deployed site leaves out archived prototypes' experiments with them. `utils/experiments.ts` (`experimentsOf`, `experimentAddress`, `viewAddress`) picks a component's from active prototypes, with the maker from the prototype's owner. Each experiment has **Open as view** (its page in its prototype, with comments) and, locally for someone registered, **Duplicate** (`LabExperimentActions.vue`). Renaming and deleting use the prototype's own tools.
  - **New experiment** (locally, for someone registered, when the component has a component file) asks for a name (`LabExperimentNameModal.vue`, through `useLabExperimentDialog`) and opens the new experiment. The handler (`server/experiments.ts`, `action: "create"`) runs `experiments/service.ts`: the first experiment of a component makes the person's “<Component> experiments” prototype with the component's system through the studio's prototype creation (`createPrototype`), its empty starting view becoming the experiment; later ones go into the prototype that already holds their experiments of it (or, failing that, the one with that title). The view starts from the component's rendering source (`experiments/source.ts`): for a component file that wraps one Nuxt UI tag, its Default example (or first) on a centred stage like the Playground's, with the examples file's script minus `Example`; for a composite (such as the sidebar) or a component without examples, the component's own source without its leading comments. Relative imports are rewritten to reach the same files from the prototype. **Duplicate** (`action: "duplicate"`) copies anyone's experiment into your own prototype for that component, with fresh permanent IDs and today's day. Refusals use the studio's sentences: someone not joined is told how to join (and the tab says so instead of offering New experiment), a name you use already is refused, an archived system or prototype refuses. The deployed site lists experiments without New experiment or Duplicate.
- **One experiment** (`pages/experiment.vue`, `/experiments/<view id>`): its name, maker, day and actions, then `components/LabExperimentStage.vue` (`data-lab-experiment-stage`), where the experiment's Breakdown mounts; until it does, the experiment's live preview. An ID that is no experiment of this component is not found, with **All experiments**. Its title reads “<experiment> — Experiments — <component> — Lab — <studio name>”.

Interface text is under `lab` in `i18n/locales/en.json`.
