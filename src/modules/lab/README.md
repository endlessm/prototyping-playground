# Lab

A bench for one system component at a time: the system's components in a list on the left and, for the open one, its title, description and tabs. It reads the Systems module's build data (`systems/catalog`, `systems/components`) and reuses its pieces, and lists experiments from the manifest. Only making and saving experiments writes files, through its handlers on the local dev server (`server/experiments.ts`, `server/save.ts`); everything else works the same locally and on the deployed site. It has a rail button (flask icon, after Systems), and no Home block, palette entries or skills.

## Addresses

Addresses use the system's permanent ID, as Systems does:

- `/lab` opens the default system's first component, or the first active system with components; it replaces itself in the history. Without any component it says "No components yet" with **View systems**.
- `/lab/<system id>` opens that system's first component the same way, or says it has none yet.
- `/lab/<system id>/<slug>` is the component's **Overview**; `/variants`, `/playground`, `/breakdown` and `/experiments` follow it, and `/experiments/<view id>` is one experiment.

The Lab offers active systems that have components (`labSystems`, the default first, then by name). An unknown or archived system, an unknown component, or an address under a component naming no tab shows "Page not found", with the component list kept and **View components** (to `/lab`) as the way back. Tab titles read "<tab> — <component> — Lab — <studio name>", and "Page not found — Lab — <studio name>" when nothing is there.

## The frame

- `pages/system.vue` is the frame: `components/LabComponentList.vue` in the section panel (`AppSectionNav`), kept on screen while the bench changes. Its header names the open system, or the **System** picker does when more than one active system has components; then **Search components** (title and address first, then description; Escape clears it; "No matching components.") and the system's components in the Systems navigation's order, the open one highlighted. Moving to another component keeps the open tab.
- `pages/component.vue` is the bench: the component's title and description, then `components/LabTabBar.vue`, a set of links ("Component tabs", the current one `aria-current`), and the open tab beside them. It gives the tabs their component through `composables/useLabComponent.ts` (`provideLabComponent` / `useLabComponent`: the system, the component, its page data from `useComponentPages`, and `reload`).
- `utils/lab.ts` holds the addresses (`labAddress`), the tabs in order (`LAB_TABS`: id, i18n label, path), the tab an address shows (`tabAt`), the systems offered, where `/lab` lands and the list's search. The tab bar, the list and the titles all read `LAB_TABS`, so a new tab is one entry there and one child page in `module.ts`.

## Tabs

- **Overview** (`pages/overview.vue`), at the Systems page's reading width: **Open in Systems**, then the component's guide (`ComponentGuide`), Source (`ComponentSource`) and Props (`ComponentProps`), as its Systems page shows them, without the examples. Files that couldn't load are listed with **Try again** (`ComponentLoadErrors`). The Systems component page links back with **Open in Lab** while this module is on and the system is active.
- **Variants** (`pages/variants.vue`): every example of the component's examples file in a grid, in the file's order, each a `components/LabVariantCard.vue`: its title as the Systems page writes it and its `SystemPreview`, so it renders alone in the system's preview document, fails alone and follows its file on disk locally. Two columns when the bench is at least 48rem wide (a container query, so hiding the component list counts), one below. An example that needs more room takes the row: `SystemPreview` emits `wide` when the example's content is wider than its frame or something in it stretches across it (a block button, a full-width table), and the card keeps the row from then on, so the grid doesn't flip as columns change. No new authoring. Under each preview, **Show code** opens that example's own code (its `<Example>` block, dedented, highlighted by the Markdown pipeline through `ComponentGuide`) and **Copy code** (named for its variant, "Copy code for Block", for screen readers) copies it with a toast, or says the browser blocked the clipboard and to copy from Show code; the snippets come in the component page data (`snippets`), with Unix line endings. The title, preview and code row of each card are rows of the grid (`grid-rows-subgrid`), so the cards of one row line up. A component without an examples file says which file to add, as its Systems page does.
- **Playground** (`pages/playground.vue`): the component file on the stage (`components/LabPlaygroundStage.vue`, in the Systems module's `SystemPreviewFrame`: its system's preview document under the component's `playground` preview ID; new props arrive by message, so it updates in place without reloading; the component sits centred on it; it grows with the component up to 70% of the window (40% on narrow screens), then scrolls inside, and stays in view while the controls scroll, beside them on wide screens and above them on narrow ones; when nothing in it takes any room, a note under it says it may need content only code can give; props that make it throw show "This component couldn’t render." with the error until the next change), beside **Props** (`components/LabPlaygroundControls.vue`, one `LabPlaygroundControl.vue` per prop), stacked on narrow screens. `utils/playground.ts` maps each prop's metadata to a control: a union of string literals is a select (optional ones without a default offer **Default**, leaving it unset), `boolean` a switch, `string` a text field, `number` a number field, anything else a "Set in code" row with its type. The Playground always opens pre-populated, so the component never starts empty: each control's start is, first, the literal attribute its component's tag has in the `Default` example (or the first example): `label="Save"`, a bare `loading`, `:size="2"`, kept only when it fits the control. `tooling/systems/example-seeds.ts` reads them on Node, from the component's own tag rather than a wrapper around it (`UInput` inside a `UFormField`), and the component page data carries them (`seeds`); computed bindings, events, directives, `class` and `style` are left out. Then the prop's literal default; then, for text that shows (`label`, `title`, `description`, `placeholder`, `text`, or any required text) still empty, a sample from its name ("Label", "Model value"), a value for the component rather than studio copy, so it isn't translated. Seeded starts reach the stage; a value equal to its start never enters the address. Each is labelled with the prop's name, its description under it as help the control is described by, required ones marked. Changed values live in the address, one query parameter each (`?color=neutral&loading=true`), replaced rather than pushed; a seeded prop emptied or set to **Default** is an empty one (`?title=`), so it stays out instead of springing back; reading it back drops unknown props and values that don't fit, and the address is rewritten without them, and **Reset** clears them, back to the seeded values (it stays enabled, keeping the keyboard where it was, and says "Values reset" to screen readers; it is left out when no prop has a control). A prop the component changes itself (a modal closed with Escape or its close button emits `update:open`) reaches the studio as the preview document's `update` message, and its control follows. Escape in the stage brings the keyboard back to the control last used, once any overlay in it has closed, so an overlay's focus trap never keeps it there. A component without props says it has none to try. A component without a component file names the file to add; props that can't be read (a component file that doesn't compile among them; the build leaves its playground out) say so with **Try again**; a required prop with no value blocks the stage, naming it (asking for a value, or saying only code can set it, with the controls disabled).
- **Breakdown** (`pages/breakdown.vue`): how the component is built, as a tree of pieces on a dotted canvas (`components/LabBreakdownStage.vue`, fed a tree and a preview ID, so an experiment view can mount the same stage). The tree is read on Node (`tooling/systems/breakdown.ts`, `readBreakdown`, carried in the component page data as `breakdown`: the tree, or why it can't be read with **Try again**): from the source a new experiment of the component starts from (`tooling/systems/start-source.ts`, `startSource`, below), so each piece has the node ID its tag has in a new experiment, through the `.vue` files it imports inside its system (the system's aliases, `~/` at the copied app source) down to Nuxt UI pieces, whose leaves are the theme slots their own templates render (`data-slot`), and icons. Plain HTML is skipped and its components lifted; a `v-for` tag is one node, marked as repeated. A node's ID is its path: `root` is the file, `>` enters a file (`root>UButton`, `root>USidebar/UPopover/Notifications>UButton`), `/` goes into a tag's content in the same file, `~2` numbers a second tag of the same name under one parent, `#` names a theme slot (`root>UButton#label`). The root card shows that source live, in the system's preview document under the component's `breakdown` preview ID, instrumented (`tooling/preview/breakdown.ts`: the start source is served beside the component file as `<name>.lab-start.vue`, made from its files, and an instrumented copy of any file as `<name>.lab-breakdown.vue`, so examples and playgrounds keep the plain file), where each tree tag reports its component to the runtime's `$lab` (`tooling/preview/runtime/breakdown.ts`) and takes its `ui` and `class` through an override store. The runtime marks each piece's elements with `data-lab-node` (space-separated IDs, since a wrapper and the tag it renders share an element), reports their boxes and theme slot boxes (`nodes` message) whenever they change, and outlines the pieces the studio names (`highlight` message). Cards (`components/LabBreakdownCard.vue`) show a dotted preview inset with their piece live (`components/LabBreakdownPiece.vue`: a frame of the same Breakdown preview at the root's width, seen through a window cut to the box its own document reports for the piece, a theme slot's element for a slot card, the first item for a piece a list repeats, at its size or shrunk to fit, centred; a piece the content doesn't render says "Not shown with this content"; `utils/pieces.ts` picks the box, widening an element that takes no room, such as Nuxt UI's sidebar, to its slots and the pieces inside it). A card's frame mounts only while the card is near the view and the zoom is at least 40%, so a large tree such as the sidebar's (115 pieces) runs a few documents at a time (at most about 30 at 41% on a 1440-pixel-wide window). Every frame hears the same host messages, routed by `composables/useBreakdownMessages.ts`. Under the inset come the name, then the file and library in monospace (`ui.<slot>` for a theme slot); a source chip on each connector says where the piece comes from (System, the system's app, Nuxt UI, the icon library, Experiment); a piece's theme slots sit in a grid under it (`utils/breakdown.ts` lays the tree out). Hovering a card lifts it and outlines its piece in the preview; clicking selects it (blue outline, its name in the toolbar); Escape or a click on the empty canvas lets go. The canvas pans (drag or scroll) and zooms (the toolbar, or ⌘/Ctrl and scroll); the toolbar (`components/LabBreakdownToolbar.vue`) also cross-fades to the component alone, kept in the address as `?view=component`, and lets the canvas cover the screen: it fills the window and asks the browser for full screen on the whole page rather than the canvas, so the knobs' popovers, which open at the page's end, still show; its button, Escape with nothing selected or leaving the browser's full screen bring it back.
  - **Knobs**: selecting a Nuxt UI piece or one of its theme slots turns the toolbar into its inspector (`components/LabBreakdownInspector.vue`): its name, then a knob (`components/LabKnob.vue`) for each thing the classes of its theme slots set, read from the classes the preview reports for each slot (`classes` in the `nodes` message): corners, padding (horizontal and vertical apart when the classes are), space between items, text size, weight, fill, text color, ring and size, labelled from the family and the slot ("Label text size"), each family with its own colour and icon (`utils/knobs.ts`). A piece whose tag lives in another file than the Breakdown's own (inside an app component it imports) has no knobs and says which file holds it ("This piece lives in <file>, so an experiment can’t change it"), since Save writes only into the experiment's own file. A piece's knobs come only from its own theme slots, the ones its slot cards name, not from Nuxt UI pieces it renders inside itself (a modal's close button). An overlay (`UModal`, `USlideover`, `UPopover`, `UTooltip`, `UDropdownMenu`) shows open in a Breakdown (the instrumentation adds `default-open` unless the tag says whether it is open), so its theme slots render and have knobs. A Nuxt UI component whose theme is one class string, with no slots (`UContainer`, `ULink`), has knobs on its own element (reported as `base`), written into its `class`. A piece without any says "Nothing to adjust on this piece". `tooling/preview/knobs.ts` maps classes to knobs and back (`knobsOf`, `knobClass`): only a slot's unprefixed classes (a `hover:` or `md:` class stays), values on Tailwind's scale shown in pixels, the theme's own text sizes among them at the size their tokens give them (`--text-body`, `--text-caption-1`; `knobTheme`), which the preview document's tailwind-merge also knows as sizes (the pipeline extends Nuxt UI's `tv.twMergeConfig`), so a knob's size replaces a theme size, colours as Nuxt UI's semantic roles, the theme's colours with opacity steps and their shades. Drag the icon sideways, type (pixels land on the nearest step) or press the arrow keys: each step goes to the nearest value that way, so a value off the scale moves to the next size up or down and stays at the scale's end, and a colour off the theme's list stays. A colour opens the theme's colours, each with a swatch of the colour the system paints it with, read in the root's preview document (the `swatches` host message, answered by `tooling/preview/runtime/swatches.ts`). Every change goes to the preview at once as the `overrides` host message (node ID → slot → classes), which the runtime merges into each piece's `ui` (Nuxt UI merges them with tailwind-merge), without reloading; the preview's stylesheet names every class a knob can write (`@source inline`, `knobSafelist`), so any value renders before a file uses it. Hovering a knob draws what it changes in its colour (`knob` host message, `tooling/preview/runtime/knobs.ts`): an outline on the corners, a hatch on padding and on the space between items, an outline on anything else. Unsaved changes live in memory for the page (`composables/useBreakdownChanges.ts`: `overrides`, `pending`, `set`, `valueOf`, `reset`, `all`, `keepOnly`); **Reset** ("Discard unsaved changes") drops them and Save counts them (`components/LabBreakdownSave.vue`). On a system component Save reads **Save as experiment**: it asks for a name and makes the experiment with the changes already written (the original never changes); a change it can't place (a piece in another file, on a tree read before an edit) makes nothing, the dialog says why and the changes stay. Leaving the page with unsaved changes asks first (`composables/useLeaveGuard.ts`, `components/LabLeaveModal.vue`; a change of the address's query, such as the canvas's view, doesn't), and so do reloading and closing the tab. Saving needs the local dev server, so the deployed site shows Reset without Save, and Save is disabled for someone who hasn't joined, who reads why (`components/LabJoinNote.vue`, the Experiments tab's note).
  - **Saving** (`experiments/save.ts`, behind `server/save.ts`, `POST { prototype, artifact, base, changes }`): it checks that the view is an experiment, that you may change its prototype (the studio's own refusals, as `canEdit` in `yarn studio context`), that the file is still the version the changes began on (otherwise “This file changed on disk since you opened it.”) and that each value is one the theme offers, then writes each change into its piece's tag (`experiments/writer.ts`, `writeBreakdownChanges`) and answers the new version, how many it wrote and those it skipped. The writer puts a theme slot's classes in that key of the tag's `ui`: an object written into a tag without one (`:ui="{ base: 'rounded-xl' }"`), a key merged into an object already there, or a bound expression spread with the key after it, keeping what the expression gives that slot (`:ui="{ ...navMenuUi, link: [navMenuUi?.link, 'rounded-xl'] }"`). A change to the piece's root slot (`base`, `root`) replaces a class of its family in the tag's static `class`, which would otherwise win over `ui`. Each new class replaces the one of the same knob family and leaves prefixed classes alone. A change to a piece inside a file the experiment imports isn't written (the file isn't the experiment's; the inspector offers no knobs there, so this happens only on a tree read before an edit): Save keeps it pending, and its confirmation says how many and why.

- **Experiments** (`pages/experiments.vue`): everyone's experiments with the component, newest first, each a `components/LabExperimentCard.vue`: its live preview (`LabExperimentPreview.vue`, the view in its system's preview document through `SystemPreviewFrame`, following its file on disk locally), its name (a link to its page), who made it and the day. An experiment is an ordinary view whose first comments name the component it explores, beside its permanent identity: `<!-- @lab-experiment <system id> <component slug> <YYYY-MM-DD> -->` (`tooling/manifest/experiments.ts` reads and writes it; the day is optional). The manifest lists them in a small summary (`experiments`: view ID, title, prototype, system, component, day), so the tab needs no prototype's artifact list; a marker naming another system than its prototype's is ignored, and the deployed site leaves out archived prototypes' experiments with them. `utils/experiments.ts` (`experimentsOf`, `experimentAddress`, `viewAddress`) picks a component's from active prototypes, with the maker from the prototype's owner. Each experiment has **Open as view** (its page in its prototype, with comments) and, locally for someone registered, **Duplicate** (`LabExperimentActions.vue`). Renaming and deleting use the prototype's own tools.
  - **New experiment** (locally, for someone registered, when the component has a component file) asks for a name (`LabExperimentNameModal.vue`, through `useLabExperimentDialog`) and opens the new experiment. The handler (`server/experiments.ts`, `action: "create"`) runs `experiments/service.ts`: the first experiment of a component makes the person's “<Component> experiments” prototype with the component's system through the studio's prototype creation (`createPrototype`), its empty starting view becoming the experiment; later ones go into the prototype that already holds their experiments of it (or, failing that, the one with that title). The view starts from the component's start source (`tooling/systems/start-source.ts`, `startSource`, the one its Breakdown shows): for a component file that wraps one Nuxt UI tag, its Default example (or first) on a centred stage like the Playground's, with the examples file's script minus `Example`; for a component file that only renders one copied app component (the sidebar), that app component's template and script in the wrapper's place, with the wrapper's markup, styles and setup lines that don't read its props; for another composite or a component without examples, the component's own source without its leading comments. Relative imports are rewritten to reach the same files from the prototype. **Duplicate** (`action: "duplicate"`) copies anyone's experiment into your own prototype for that component, with fresh permanent IDs and today's day. Refusals use the studio's sentences: someone not joined is told how to join (and the tab says so instead of offering New experiment), a name you use already is refused, an archived system or prototype refuses. The deployed site lists experiments without New experiment or Duplicate.
- **One experiment** (`pages/experiment.vue`, `/experiments/<view id>`): its name, maker, day and actions, then `components/LabExperimentStage.vue` (`data-lab-experiment-stage`): the experiment's own Breakdown, the same stage as a component's, fed by the Lab's build data `lab/experiments` (`experiments/trees.ts`: each experiment's tree read from its own file, the preview ID of its instrumented copy, `experimentBreakdownId` in `tooling/systems/preview-ids.ts`, which the manifest adds to its system's preview document, and the file's version), so the deployed site has it too and it follows the file after a save and after any edit on disk; until it arrives, the experiment's live preview; a file whose structure can't be read says so with **Try again**. Locally, Save writes into the experiment's file when it is yours (`isOwnPrototype`, the ownership half of the prototypes module's `useMayChange`); for anyone else registered, Admins included, it reads **Save as my experiment**, which copies the experiment into their own with the changes written (`server/experiments.ts` takes `changes` with `create` and `duplicate`). An ID that is no experiment of this component is not found, with **All experiments**. Its title reads “<experiment> — Experiments — <component> — Lab — <studio name>”.
  - **Dial panel**: with the component alone on the canvas (`?view=component`), a [DialKit](https://dialkit.dev) panel, **Controls**, sits docked at the canvas's right edge (`components/LabDialPanel.vue`), the component starting centred in the room left of it; the Breakdown hides it. It has a folder for each piece with knobs, named as its card is (`UButton`), holding the inspector's knobs (`pieceKnobs` in `utils/knobs.ts`, shared with the inspector) as selects over the theme's own values only, each named by its class value and size (`lg · 8 px`, `knobChoices`). It reads and moves the page's `useBreakdownChanges`, so the inspector, Reset, the count and Save see its changes and it shows theirs; Reset and Save stay in the toolbar beside the component too. DialKit's own controls (`Folder`, `SelectControl` from `dialkit/vue`) are laid out by the Lab rather than through `DialRoot`, whose labels rewrite names (`UButton` reads “U Button”) and whose Copy and versions toolbar keep values the studio wouldn't save; so it shows on the deployed site too, with Save left out as everywhere there. It is light, as the studio is, and turns dark with Nuxt UI's `dark` class. DialKit and the motion libraries it brings load with the panel, when the component view first opens (`defineAsyncComponent`); its stylesheet comes with it, scoped to `.dialkit-*` classes, without the web font it would fetch from Google.

Interface text is under `lab` in `i18n/locales/en.json`.
