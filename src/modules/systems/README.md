# Systems

The Systems area: each design system's Overview, Libraries, Context and Skills, with the Theme, Assets and Components its navigation lists. The studio always has it (required), with a rail button (shapes icon) and a Home block. Systems themselves live in `src/systems/<key>/`, registered in `studio.config.json` (`tooling/systems/registry.ts`); there is no built-in "Studio" system: the studio's own interface is plain Nuxt UI.

- `module.ts` declares the module, its pages and its build data.
- `pages/index.vue` is `/systems`, the collection.
- `pages/system.vue` is `/systems/<system-id>`, the frame: the system's navigation (`components/SystemNav.vue`) in the section panel, kept on screen while its child pages change, each starting at the top. Its children are `overview.vue` (the address itself), `libraries.vue`, `context.vue` and `skills.vue` (the sections), `context-document.vue` and `skill-document.vue`, `theme.vue` (`/colors`, `/typography`, `/radius`, `/shadows`, `/spacing`, `/motion`, `/effects`, `/tokens`, drawn by `components/SystemThemeFrame.vue`), `assets.vue` (`/fonts`, `/icons`, `/images`), `asset.vue` (`/<kind>/<path>`, with `components/SystemFontPreview.vue`), `component.vue` (`/components/<slug>`, see Component pages) and `missing.vue` (anything else: "Page not found", with the navigation kept).
- `components/SystemsHome.vue` is the Home block: up to three active systems, the default first, and a link to the collection.
- `composables/useSystemCatalog.ts` loads the build data; `utils/pages.ts` holds the addresses and source files of a system's pages.

Addresses use the system's permanent `studioId`, so they survive renames: `/systems/<id>`, `/libraries`, `/context/<path>` (the file without `.md`), `/skills/<skill>/SKILL` and a skill's other documents (`/skills/<skill>/references/steps`) and text files, with their extension (`/skills/<skill>/scripts/check.mjs`), the theme pages, `/fonts`, `/icons`, `/images` and `/components/<folder>`. Tab titles read "<page> — <system> — Systems — <studio name>".

## Build data

The catalog (`tooling/systems/catalog.ts`) is computed on Node from each system's folder, refreshed in development when a file in the systems folder changes:

- `systems/catalog`: per system, its label, status, folder and colour modes; the Overview's `summary`, `guidance` and `code` (from `system.ts`'s `overview`); its libraries with the installed version (`null` when the package isn't installed); its theme tokens (`tooling/systems/tokens.ts`: the custom properties `app.stylesheet` and every stylesheet it imports set on `:root`, `:host`, `.light`, `.dark`, the system's `themeClass` or in `@theme` blocks, its own files and its packages' alike, so Tailwind's theme and Nuxt UI's roles count; `--x-*: initial` resets a namespace; a Nuxt UI system also gets its `app.nuxtUi.colors` and their palettes, which Nuxt UI sets at runtime. Each token once, by page: colours, typography, radius, shadows, spacing, motion, effects, other, with its declared value, its Nuxt UI role section and utility, its ramp, and whether it has a dark value. There is no hand-kept copy of the tokens); the Icons page's sample (`icons` in `system.ts`: `snippet`, `href`, Iconify `names`); components (see Component pages: each with its title, description, `source` note and `docs` link from its page's frontmatter, its files, and its examples with their preview IDs); its assets (`systemAssets`): local ones in `assets/` (fonts by extension, `icons/` as icons, other images as images) and, for a system with copied app source (`app.source`), that source's `assets/images/` (its `Icons` folders as icons, the rest as images); Context documents in file-tree order with their folders; and one entry per skill, with its files, `SKILL.md` first.
- `systems/components`: each component page's Markdown and examples text and its props, by `<system id>/<slug>`, loaded when a component page first opens (`componentPages`). Props are read from the component file with Vue's component metadata tooling (`tooling/systems/props.ts`, `vue-component-meta`); a file that can't be read is listed under the page's errors instead.
- `systems/documents`: the Markdown text of Context and Skills, and the text of skills' other files (a script), by repository path, loaded when a document first opens. Binary files (`tooling/systems/text-files.ts`: pictures, fonts, archives and the like by extension, or content with NUL bytes or invalid UTF-8) are left out.

The catalog also gives the system's own Overview content: an `overview.vue` in the system's folder, shown below the Overview's blocks. The dev server and the build add a system's component examples and its `overview.vue` to its preview document's views (`systemPreviews`), each under a fixed ID derived from the system, component and example (`tooling/systems/preview-ids.ts`), and watch the systems folder so open documents follow changes.

The deployed site gets active systems only: archived ones, with their documents, stay out of the build. The dev server and the build warn about a system's Context and Skills (`systemContentProblems`): Context holds Markdown documents; each skill is a folder with a `SKILL.md` whose frontmatter names it as its folder (lowercase words and single hyphens, at most 64 characters) and describes it (at most 1024 characters).

## The collection

"Systems", with "Components, styles, assets, and guidance for your prototypes." Each system is a card (name, summary or a generic line, "Used by N prototypes") or a list row, by the shared cards/list preference (`useCollectionView`, remembered in this browser as `design-studio:collection-view`, shared with other collections). The default system comes first with a **Default** badge, then the others alphabetically; archived systems sit in a muted **Archived** section below. The search ("Search systems", kept in `?q=`) matches the ID, folder, name, description and the word "Default"; no match shows "No matching systems" with **View all systems**.

Locally, Admins see **New system** in the header (see "System lifecycle").

Each card, row and navigation header has the system's "…" menu ("Actions for <Name>", `components/SystemActions.vue`, its content in `utils/actions.ts`), in the prototype menu's groups: **Open in editor**, **Show in Explorer** / **Reveal in Finder** / **Show in folder**, **Copy link** and **Copy path** (`src/systems/<key>/`); then **Rename** (Admins and the system's maintainers), **Set as default** (Admins; on the default it reads **Default system**, disabled) and **Archive** (Admins); then **Delete** (Admins), alone and in red. Locally the reach actions are for registered contributors; the deployed site offers only **Copy link**. An archived system's menu has only **Restore** and **Delete**, for Admins, and no menu for anyone else.

## A system

The navigation shows the system's name, its "…" menu and, for the configured default, "Default system". Its **Resources** toolbar has **Search** and **Expand all / Collapse all** (off while searching). Entries, in order: Overview, Libraries, Context, Skills, Theme, Assets, Components. Branches start open, fold with their chevrons, and stay as left for the session in this page (a reload opens them again); the branch holding the current page opens. Context and Skills are the shared file tree as branches (see "Context and Skills files"): Context with its folders and documents, Skills with each skill as its folder and the skill's other files under it ("Empty folder" without any). Theme lists only the pages its tokens fill ("No tokens yet" without any); Assets always lists Fonts, Icons and Images; Components lists documented components ("Empty folder" without any). Hovering a branch shows its folder, an item its file. Search ("Search system") filters by names and file paths, and Libraries by its libraries' names and descriptions, opening what matches; Escape clears it, a second Escape closes it; "No matching items." when nothing matches. Right-click a page for **Edit source** (locally, with its shortcut), **Copy link** and, locally, **Copy path**; only Context and Skills files are made, renamed, moved or deleted here.

- **Overview**: the name and summary (or "The guidance and code included in <Name>."), then three blocks. **Instructions**: Context documents and Skills, with the authored guidance or "No system instructions have been added yet.". **Toolkit**: Components, Theme tokens and Assets (local and copied app ones, never package files), the authored code sentence and the colour modes. **Where it’s used**: active prototypes, the three newest (title and owner) and "View prototypes using this system" (`/prototypes?system=<id>`), or "No active prototypes use this system yet…". An archived system says so.
- **Libraries**: "The sources and tools behind <Name>.", each library as an entry with its anchor (`#<id>`), version ("v1.2.3", or "Not installed" with "Ask your agent to install this dependency."), description, links to the pages it supplies (Typography for fonts, Fonts, Icons, Images, and the components a package documents) and **Docs** in a new tab. A library declares those pages with `assets: ['fonts' | 'icons' | 'images']` and `components`.
- **Context** and **Skills**: the section itself says what it is for, "Select a file in navigation…" or "No files yet. Ask your agent to add useful material.", and that being listed doesn't load a file into a conversation. Documents read through the studio's shared Markdown reader (`components/SystemDocument.vue`, the pipeline of prototype documents and the Manual): GitHub Markdown, the title from the frontmatter or first heading, raw HTML shown as text, Mermaid and highlighted code, and relative links (mapped with `provideMarkdownLinks`) to the system's other documents, and to a skill's text files, opening in the studio. A skill's other text file (a script in its folder) opens read-only as its text under its path (`app/components/TextFileReader.vue`): locally in the source editor, highlighted; on the deployed site as plain monospace text. Binary files have no page ("Page not found").
- **Theme**: a page per token kind the stylesheet fills, and always Typography for a system with a stylesheet, each with a one-line description and the tokens drawn inside the system's own preview document (`<base>_preview/<id>/?theme&session=<id>`, `tooling/preview/runtime/theme.ts`, channel `tooling/preview/theme.ts`): the document's app comes from the system's factory, so samples use the system's stylesheet, fonts, background and colour modes, and the colours Nuxt UI sets at runtime. Each value is measured on the document's root and measured again when its colour mode or a stylesheet changes; a token the browser doesn't hold shows its declared value, and "not set" without one. Values too long for their column show in full on hover. **Colors**: a swatch, the name (a Nuxt UI role's utility on hover), its purpose and value, grouped Text, Surfaces, Borders and Theme colors (Nuxt UI's roles, labelled in the locale file), then ramps by name ("Amber", "Primary"), then "Other colors". **Typography**: families with a pangram, sizes with their line heights, weights, then other type tokens, and a note when sizes or weights aren't declared. **Radius**, **Shadows** (box, drop and text shadows each sampled their way), **Spacing** (bars, with container widths apart), **Motion**, **Effects** and **Other tokens** list each value. The frame grows to fit; ⌘' / Ctrl+' inside it opens the stylesheet. The studio sends the tokens again when the stylesheet changes.
- **Fonts**, **Icons**, **Images**: always present, in the studio's own look. Each lists first the libraries that supply that kind ("Icon library", linking to their Libraries entry), then, on Icons, the system's icon sample (snippet, **Browse all icons**, a grid), then "Local <kind>" (files in `assets/`) and "App <kind>" (the copied app's images) with thumbnails, or "No local <kind> added" with what to ask the agent. An asset opens its page (`/<kind>/<path>`): a link back, its name, its path, a picture (an `<img>`, so an SVG's scripts never run) or a font loaded under a name of its own ("Loading font", "This font could not be previewed.", unloaded on leaving), and its repository path. Asset pages have no source mode. The files come from `<base>_system-assets/<id>/<file>` (`tooling/systems/serve-assets.ts`): in development, only files the pages list; in the build, copies of those files for active systems.
- **Overview content**: a system may add `overview.vue` to its folder; it renders below the blocks in the system's preview document, in the system's own look ("<Name>’s own overview").

## Component pages

A component is whatever files share a name in `components/`, in a folder of its own (`button/button.vue`, with `index.ts` re-exporting it) or flat (`IconButton.vue`); any one of them makes a page at `/components/<slug>` ("IconButton" → `icon-button`), listed under Components in the navigation (`tooling/systems/components.ts`):

- `<name>.vue`: the component. Its props table reads `defineProps`, its defaults and its doc comments.
- `<name>.md`: the page. Frontmatter `title` and `description` (required), `source` (a sentence on where it comes from) and `docs` (its documentation elsewhere); a `## When to use` section (required); anything else is optional.
- `<name>.examples.vue`: live examples. Each `<Example name="…">` (imported from `#studio/examples`) is one example, in the file's order, titled in sentence case ("WithIcon" → "With icon"). Write examples as screens write them.

The page reads, in order: the title and description; the Markdown page (the shared Markdown pipeline, its headings sized to the page's sections); **Examples**, each rendered alone in the system's preview document (`components/SystemPreview.vue`), in a frame as tall as its content, with **Show code** below showing the examples file highlighted; **Source**, with links to the libraries that list the component (`components` in a library, to its Libraries entry), the `source` sentence, **Component docs** and the file's path; then **Props**, closed at first and labelled "1 component · N props": Prop, Type and Default, required props marked "*", descriptions as tooltips on prop names, long types and defaults cut with the whole text on hover or focus, and "No props." or "Also accepts every native attribute of the element it renders." (unless the component sets `inheritAttrs: false`). Missing parts say which file to add ("No page yet. Add <name>.md…", "No examples yet. Add <name>.examples.vue…"). An example that throws shows "This example couldn’t render." with its error in its own frame; the other examples and the page still show. Files that can't load (a component whose props can't be read) are listed under "Some component files couldn’t load." with **Try again**. Pages follow their files on disk.

Documentation gaps (a component without a page or examples, a page without `title`, `description` or "When to use", an examples file without examples, two components with one address) are checked at dev start and in the build, as one warning per system listing the first five (`systemDocsReport`). A system's `docs` setting decides: `'warn'` warns, `'strict'` stops the build (and warns in dev), `'off'` stays silent.

`yarn component-docs <system> [component] [--yes]` (also `yarn studio component-docs`) adds the examples file and page a component is missing, or every component's, from templates (`tooling/systems/scaffold.ts`): a flat component first moves into a folder of its own with an `index.ts`, the first example fills required props (simple types with a value, others with `undefined` to replace), and files that exist are never touched. Without `--yes` it prints what it would do.

## System lifecycle

Admins create systems and choose the default; Admins and a system's maintainers rename it; Admins archive, restore and delete it. The studio command and the menus share the same plans (`tooling/systems/lifecycle.ts`): `yarn studio create-system <key> [--label <name>]`, `rename-system <key> --label <name>`, `archive-system <key>`, `restore-system <key> [--restore-prototypes]`, `delete-system <key>` and `configure --system <key>` (the default), each previewed before `--yes`, printing a JSON result when applied. `yarn studio remove <key>` deletes a system nothing uses: never the only or the default one, and `--force` when prototypes use it or documents link to it.

- **Create**: a name (plain text, 1–120 characters, starting with a letter) becomes the folder key (accents stripped, lowercased, hyphens), which no other system or module may use. The system is made from `tooling/studio/templates/system/`: an empty Vue app (`app.ts`), an empty theme scope (`styles/theme.css` on `.<key>-theme`), both colour modes, Vue as its one library, its own workspace (`package.json`, `@studio-system/<studioId>`), `README.md`, `AGENTS.md` routing to its `context/` and `skills/`, and a fresh permanent ID. It is registered in `studio.config.json` with no maintainers; the default system and existing content don't change.
- **Rename**: the name, folder, registration and references to the folder (`systems/<key>` paths in the studio's text files) change together; the permanent ID (so its address), the default choice, prototype assignments, pending rebuilds and maintainers stay. Files still naming the old folder are listed in `renameReview` in `system.ts`: the Overview shows "Some references need review" with **Copy cleanup instructions** until an agent removes it.
- **Archive**: refused for the default system. The system's status becomes `archived`, and its active prototypes are archived with it (`archivedBySystemId` in their `meta.json`). Archived systems stay browsable locally, read-only, with an alert on their Overview, and leave the deployed site.
- **Restore**: the system alone, or with the prototypes archived with it. It never becomes the default.
- **Delete**: refused for the default system. The folder is deleted for good; its registration and maintainers go; pending rebuilds that targeted it are cancelled. Its prototypes keep their files and `systemId` and get `systemMissing: { systemId, label }`: their views show "Rebuild needed", their header "System deleted" with the rebuild instructions, and they stay out of the deployed site until an agent rebuilds them (see the prototypes README).

Only one system change runs at a time (the `.studio-system-operation` marker in the studio's root); another says "Another system change is in progress. Try again when it finishes." A change writes its files, moves or deletes the folder, refreshes `yarn.lock` (`yarn install --mode=update-lockfile`, for systems in the `src/systems/*` workspaces) and checks that the systems still load; any failure puts every file, the folder and the lockfile back ("Nothing was made." / "Nothing was changed."). Before anything moves, the folders it would move are probed: on Windows a folder another program holds (an editor, a terminal, a running dev server) can't be renamed, so the preview and the dialog name the holder and the confirm button stays off. Folder moves fall back to copy-then-remove (`tooling/files/folder-locks.ts`).

In the studio, the dev server's file service does it (`POST <base>_studio/files/systems`, `tooling/files/systems.ts`), after its own file watchers let go of the folder (`tooling/files/watchers.ts`). A change restarts the dev server once the marker is gone (a change rolled back doesn't). The tab that asked shows one full-window status screen across the restart (the restart handoff's system change kind, `tooling/restart/handoff.ts`), in the studio's colours, announced politely, with the app inert: "Creating <Name>", then "Opening <Name>", landing on the new system's Overview in place of the collection in the history; "Deleting <Name>", landing on the collection once the system is gone from it; and "Renaming", "Archiving", "Restoring" or "Making <Name> the default". After 30 seconds it offers **Reload studio**; one older than 2 minutes is forgotten; reduced motion stops the spinner and the fade. The confirmation ("System renamed. References updated.", "System and associated prototypes archived.", "System restored.", "System deleted. Associated prototypes need a rebuild.", "<Name> is now the default system.") shows once, on the page after the reload. Archiving and deleting land on the collection; the other changes stay on the page. A refusal returns to the dialog with its message, without sending again.

The dialogs (`components/SystemNewModal.vue`, `SystemRenameModal.vue`, `SystemLifecycleModal.vue`, through `useOverlay`, loaded only in development): **New system** ("Create a place for your components, theme, assets, and guidance. Then set it up with your agent.", Name, **Cancel** / **Create**); **Rename system** ("Enter the new name.", **Cancel** / **Save**); **Archive <Name>?** (lists "Also archives N prototypes" with links, **Cancel** / **Archive system**; for the default system "<Name> is the default system" with **Close**); **Restore <Name>?** (**Restore system only** / **Restore system and prototypes**); **Delete <Name>?** ("This permanently deletes the system’s files. Studio cannot undo this.", the dependent prototypes with links, marked "(archived)" or "(pending rebuild)", **Cancel** / red **Delete system**). The archive, restore and delete dialogs first ask the service to check the change (`<op>-check`) and keep their button off until it passes.

## Setting up a new system

Locally, an active system with no `setup` record offers its setup panel (`components/SystemSetup.vue`) on its Overview: instead of the blocks while it is completely empty (no tokens, components, assets, Context or Skills: "This system is empty. Choose how you want to build it."), otherwise behind **Curate or bring in a system**. Three blocks: "1. Choose your system foundation" (**Bring in a Vue app** or **Start from Nuxt UI**), "2. Add your setup details" (the app or library to bring in, or a DESIGN.md; what you want to build; components you already want; all optional, kept per path while the page is open, never saved) and "3. Copy and send your prompt": the prompt (`utils/setup.ts`), always visible and selectable, naming the system by name and key and the [setup-design-system](skills/setup-design-system/SKILL.md) skill, with **Copy prompt** ("Prompt copied", then "Paste into your agent’s chat and send to continue."). Once an agent saves a `setup` record in `system.ts` (`stage`, `summary`, and optionally `next`, `sources` and `record`), the panel is gone for good; the record stays as the agent's context and isn't shown.

## Source mode

Locally, ⌘' / Ctrl+' (or `?mode=source`) switches a page to its source and back; ⌘S / Ctrl+S saves; **Done** returns; leaving with unsaved changes asks first. The Overview and Icons open `system.ts`, theme pages the stylesheet, documents themselves. A component page's source has tabs, **Page**, **Examples** and **Component** (when it has a component file), one file each (`components/ComponentEditor.vue`); a missing page or examples file says so with **Create files** ("Create the files this component is missing, from a template."), which runs the same scaffold. A skill's source has a file picker ("Skill source file") for its supporting files; files that aren't text say "This supporting file cannot be edited as text in Studio.". Switching files or tabs with unsaved changes asks first ("Discard your changes?": **Keep editing** / **Discard**). Source mode never renders the page, so a broken file can still be fixed. "Loading editor…" shows while the editor loads.

The dev server's file service reads and saves through `GET|PUT <base>_studio/files/system-source`, and creates a component's missing files with `POST` (`{ system, component }`), (`tooling/files/system-source.ts`), addressed by the system's permanent ID and a path inside its folder. Only `system.ts`, the stylesheet, files inside `components/`, Context documents and skills' files are reachable. Saving needs an Admin or one of the system's maintainers (`systemMaintainers`), an active system, and the version that was read (a change on disk since is a conflict). A skill's `SKILL.md` saved out of the Agent Skills format is still saved, and the save answers with the problems the build would report (`skillProblems`), which the editor shows after "Saved". Others read, and the editor says why. The deployed site has no source mode, no file actions and no Copy path.

## Context and Skills files

The navigation's Context and Skills are the shared file tree (`app/components/files/FileTree.vue`) as branches (`components/SystemContentTree.vue`): the heading links to the section's page and folds it with its chevron, "Empty folder" shows when the section has nothing, the navigation's Search filters it (a section whose name matches shows whole) and its **Expand all / Collapse all** covers the folders, which stay as left for the session. Locally the tree lists the real files from the dev server's file service (`composables/useSystemTree.ts`, `GET <base>_studio/files/system-tree?system=<id>`, `tooling/files/system-tree.ts`), live as they change on disk; on the deployed site, and until the service answers, the catalog's (`utils/trees.ts`). Context documents show their titles and open their pages; each skill is its folder, titled from its name, opening its `SKILL.md`'s page, with its other files under it (documents and text files open their pages; binary files have none). Hovering a row shows its repository path; right-click for **Edit source**, **Copy link** and **Copy path**, as for the pages.

An Admin or one of the system's maintainers changes them while the system is active and the studio runs locally (everyone else gets the same tree read-only), under the sections' rules (`tooling/systems/content-rules.ts`, checked again by the file service, each refusal a sentence that says what to do instead):

- **Context**: "+" and a folder's menu offer **New document** (a Markdown file: `.md` is added to a name without an extension, and another extension is refused with "Context documents are Markdown files, and end in .md.") and **New folder**, each named in an inline field; a new document starts with its title as a heading and opens. Rows rename (F2 or the menu; a document keeps `.md`), drag into folders or below the rows to the top level, within Context only (there is no order to keep, so rows don't reorder), and delete after asking, to the Recycle Bin or the Trash.
- **Skills**: "+" opens **New skill** (`components/SystemSkillModal.vue`): **Name** (lowercase letters and numbers in words joined by single hyphens, at most 64 characters, also the folder's name) and **Description** ("What it does, and when to use it.", at most 1024 characters), each checked as you type and saying what's wrong once there's something to be wrong about; **Create skill** stays off until both pass. The dev server makes the folder and a starter `SKILL.md` with the name and description in its frontmatter (`skillTemplate`), and the skill's page opens; a name that is taken comes back in the dialog.
- **Inside a skill**: a skill's menu, and its folders', offer **New file** and **New folder**. Renaming the skill renames its whole folder and the `name` in its `SKILL.md`, and needs a valid skill name; deleting it deletes the whole folder. `SKILL.md` isn't listed apart from its skill, and the file service refuses renaming, moving or deleting it alone ("SKILL.md has to keep its name: it’s how agents find the skill.", "…has to stay in its skill’s folder.", "A skill needs its SKILL.md. To remove the skill, delete its folder."). A skill's folder can't be dragged ("A skill’s folder stays in skills/. Rename it, or delete it."); its files move between skills, never loose into `skills/`.

The open page follows a rename or move of its file, or of a folder it's in (addresses are the files' paths), and a deleted page leaves for its section. The changes go through `POST <base>_studio/files/system-tree` (`op`: `create`, `skill`, `rename`, `move`, `delete`; `server/system-tree.ts`), which has the dev server's watchers let go of a folder before moving or deleting it. Unlike prototypes, links to a moved Context document aren't repaired, as in the React studio.

## Command palette

The Systems group lists registered systems as "<Name> system", in both the local studio and the deployed site (active systems only there). Choosing one opens its overview. The current system stays disabled on all its pages. The module declares `paletteSource` and `paletteOrder`; the studio builds the entries from the manifest.

Locally, the group also offers what the menus offer you: **New system** for Admins (the module's `palette` entry, `localOnly` and `adminOnly`, to `/systems?new=system`, which the collection's New system button answers by opening its dialog), and, on a system's pages, that system's changes from its "…" menu (`tooling/systems/menu.ts`, shared with the menu): "Rename <Name>", "Make <Name> the default system", "Archive <Name>", "Restore <Name>" and "Delete <Name>", to `/systems/<id>?action=<id>`, which the navigation's menu answers by running the same action once it knows who you are. The address loses its `?new` or `?action` either way.
